Category: bug

## What I was trying to do

While picking forms to test (`list_forms`), I filtered for `status ==
"published"` to find the current, live version of each form, expecting at
most one published version per `parent_id` at any time (with older versions
moved to `archived` once superseded, which is what I *did* observe for
some version chains).

## What happened

For the "Patientenaufnahme" form (`parent_id`
`237bacbe-3583-444d-8bac-adc98c18c0a8`), `list_form_versions` shows:

```
1.5.0-draft  - draft
1.4.0        - published   (createdAt 07:22, published/updated 07:23:53)
1.3.0        - published   (createdAt 07:07, published/updated 07:09:20)
1.2.0        - archived    (archived at 07:09:26 - i.e. right after 1.3.0 published)
1.1.0        - archived    (archived earlier, when 1.2.0 published)
```

1.1.0 and 1.2.0 were correctly archived when the *next* version was
published (1.2.0 archived 6 seconds after 1.3.0's publish timestamp - looks
like an automatic supersede-on-publish step). But 1.3.0 was never archived
when 1.4.0 was published nearly 15 minutes later - its `status` and
`updatedAt` are unchanged since its own publish. So `list_forms`/
`list_form_versions` currently report **two simultaneously "published"**
versions of the same form (1.3.0 and 1.4.0), which is what produced 11
"published" rows for only 8 distinct form identities when I did a naive
`status == "published"` filter over `list_forms`'s output.

`list_form_versions`'s own `latestPublished` field does correctly resolve
to 1.4.0, so anything that consistently uses that field is fine - but
anything (a host app, an integration, or just a human) filtering
`list_forms` by `status == "published"` directly will see stale duplicate
"published" forms with no way to tell which one is actually current.

## What I expected

Publishing a new version should reliably archive the previously-published
version of the same form, the same way it did for the 1.1.0 -> 1.2.0 and
1.2.0 -> 1.3.0 transitions. The 1.3.0 -> 1.4.0 transition suggests this
supersede step is either flaky, order-dependent, or was skipped for that
particular publish (possibly because 1.3.0 was itself edited/republished
in between - worth checking the publish code path for a case where the
"archive previous published version" step doesn't fire).
