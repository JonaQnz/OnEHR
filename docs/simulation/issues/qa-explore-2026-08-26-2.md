Category: bug

## What I was trying to do

Verify the documented safety property of `submit_form_session_to_provider`:
"Validate first; a stale/unvalidated submission can be rejected." I deliberately
tried to submit a session whose values had changed *after* the last
successful validation, to see whether the stale `validatedRevision` would be
rejected.

Steps, on a fresh "Aktuelle Medikation" session for patient `QA-2026-0826-001`
(session id `c4150956-88b9-4b58-ac98-30d9e91830a5`):

1. `patch_form_session` with `medication_item_name: "Ibuprofen 400mg"` -> revision 1
2. `validate_form_session` -> valid, revision bumped to 2
3. `patch_form_session` again, changing
   `medication_item_name` to `"Ibuprofen 600mg CHANGED-AFTER-VALIDATION"`
   (never re-validated) -> revision 3
4. `submit_form_session_to_provider({ id, validatedRevision: 2 })` - i.e.
   deliberately citing the stale, pre-edit revision.

## What happened

The submission succeeded anyway:

```json
{
  "session": { "status": "submitted", "revision": 5, ... },
  "provider": {
    "reference": "1a3de7da-...::...::1",
    "lifecycleState": "complete",
    "changeTypeConfirmed": true
  }
}
```

The composition that landed in EHRbase contains
`"Ibuprofen 600mg CHANGED-AFTER-VALIDATION"` - the value that was never
actually run through `validate_form_session` - even though I passed a
`validatedRevision` that no longer matched the session's current revision
at submit time.

## What I expected

Per the tool's own description ("a stale/unvalidated submission can be
rejected"), I expected the mismatch between the passed `validatedRevision`
(2) and the session's actual current revision (3, post-edit) to cause a
rejection (or at minimum a warning requiring re-validation before
submission would proceed). Instead the check appears to be a no-op:
`submit_form_session_to_provider` accepted arbitrary post-validation edits
without re-validating them. In a real clinical workflow this means a
clinician (or, more realistically, a host application with a bug) could
submit data that was silently modified after the "this is valid" check ran,
and the platform would write it to the patient's record anyway. Given this
same values-replace-wholesale-on-patch design (`patch_form_session` always
replaces the full values object), a race between two tabs/sessions could
also produce this same stale-submit scenario unintentionally.
