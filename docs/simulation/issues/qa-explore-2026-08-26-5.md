Category: bug

## What I was trying to do

Look up this session's own patient's form-session history via
`list_form_sessions({ patientId: ... })`, using the same patient identifier
value (`bd84ba31-7c51-4a91-81c7-488feff8a822`, the internal registry id
returned by `create_patient` and accepted by `launch_form`'s
`patient.id` and `start_composition_session`'s `patientId`).

## What happened

`list_form_sessions({ patientId: "bd84ba31-7c51-4a91-81c7-488feff8a822" })`
returned `[]` even though two sessions had just been submitted for that
exact patient. Re-reading the actual session objects returned by
`launch_form`/`submit_form_session_to_provider`, they carry
`"patientId": "QA-2026-0826-001"` - the *external* MRN, not the internal
registry id. Retrying `list_form_sessions({ patientId:
"QA-2026-0826-001" })` returned the expected sessions.

So across this one MCP surface, a parameter literally named `patientId` has
two incompatible meanings depending on which tool you call:

- `launch_form({ patient: { id } })` and
  `start_composition_session({ patientId })` want the **internal registry
  id** (`create_patient`'s/`get_patient`'s `id` field).
- `list_form_sessions({ patientId })` wants the **external MRN**
  (`create_patient`'s/`get_patient`'s `patientId` field).

## What I expected

The same parameter name should mean the same thing everywhere, or if two
genuinely different identifiers are needed, the parameters should be named
differently (e.g. `patientRegistryId` vs `externalPatientId`) so the type
signature makes the distinction obvious instead of failing silently with an
empty array. As it stands this is an easy trap: the empty-array result
gives no hint that the *value* was wrong rather than there being no data,
and it's worse now that `sync_patients` can overwrite the external
`patientId` entirely (see `qa-explore-2026-08-26-1.md`), meaning even the
"correct" value for this parameter can change out from under a caller
without warning.
