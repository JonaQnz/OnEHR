Category: bug

## What I was trying to do

General exploratory QA pass (no specific case brief). Created a new patient
via `create_patient` with a meaningful external MRN:

```
create_patient({
  patientId: "QA-2026-0826-001",
  firstName: "Erika", lastName: "Testfrau",
  birthDate: "1978-11-03", gender: "weiblich"
})
```

This returned a patient record with `patientId: "QA-2026-0826-001"` and a
separately-generated `ehrId: "64abd847-b9b8-4ba9-af74-df7ea5872ac4"` - two
distinct identifiers, as documented ("A stable external patient identifier
(e.g. an MRN), not a database id").

I then filled and submitted two forms for this patient (Patientenaufnahme,
Diagnosen/Vorerkrankungen), and separately called `sync_patients` (to check
whether `hasPersonArchetype` refreshes after submitting a Person
composition - it doesn't without a sync, see companion issue
`qa-explore-2026-08-26-4.md`).

## What happened

After `sync_patients`, `get_patient`/`list_patients` for this same patient
now show:

```
"patientId": "64abd847-b9b8-4ba9-af74-df7ea5872ac4",   // <- was "QA-2026-0826-001"
"ehrId":     "64abd847-b9b8-4ba9-af74-df7ea5872ac4",
```

`sync_patients` silently overwrote the patient's local `patientId` (the
external MRN I explicitly set at registration) with the internal `ehrId`
GUID, discarding the original identifier entirely. Checking the other 17
patients in the registry, every single one has `patientId === ehrId` -
suggesting this isn't limited to my test patient; any natively-created
patient with a real external MRN gets that MRN clobbered the next time
`sync_patients` runs.

Form sessions created *before* the sync still carry the old
`patientId: "QA-2026-0826-001"` string as a snapshot (since it was copied
into the session at launch time), so `list_form_sessions` filtering by the
old MRN still incidentally works for historical sessions - but the patient
record itself no longer has any way to look itself up by that MRN, and any
new session/lookup keyed on it will fail.

## What I expected

`sync_patients` (reconciling with EHRbase) should never overwrite a
locally-registered external `patientId` that was explicitly provided at
`create_patient` time. At most it should populate/refresh `ehrId` and
`hasPersonArchetype`; the MRN is the whole reason `patientId` and `ehrId`
are modeled as two separate fields in the first place. As it stands, this
is a real MRN-loss bug - the exact kind of thing that breaks cross-system
patient matching in a real deployment.
